# Code Review · 代码审查

Diff → 多轴扫描 → 分级问题 → 修复补丁。审出问题不是目的，能合进主干才是。

## 何时使用

- 合并前的任何改动
- 用户贴出一段代码求挑毛病
- 排查"这段代码有没有坑"

## 工作流

### 第 1 步：先懂意图，再挑毛病
用一句话概括这次改动想干什么。看不懂意图的 review 是耍流氓——先问，别猜。

### 第 2 步：五轴扫描（按优先级）
1. **正确性**：边界条件、空值、错误路径、并发
2. **安全**：注入、密钥硬编码、输入未校验、越权
3. **性能**：N+1、循环内 IO、无界缓存
4. **可测**：改动是否可测？有没有把测试删了/改弱了
5. **可读**：命名撒谎、magic number、注释与代码不符

### 第 3 步：分级输出
每个问题带严重度，只对高危项要求必修：

```
🔴 严重（必修）——会造成资损/数据错误/安全漏洞
🟡 一般（应修）——性能或可维护性明显受损
🟢 建议（可选）——风格与一致性
```

### 第 4 步：补丁优先
高危问题直接给出可粘贴的修复代码，而不是"建议考虑"。修不完的列成带编号的跟进清单。

## 质量检查

- [ ] 每个问题都指向具体行号/代码位置，不是泛泛而谈
- [ ] 严重度判断有理由（不吓唬人也不放水）
- [ ] 给了补丁或明确的跟进清单
- [ ] 没有为了凑数提纯风格意见

## 输出格式

一句话意图确认 → 分级问题清单（位置+理由+补丁）→ 合并判定（可合/修后可合/阻塞）。
